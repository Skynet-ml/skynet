# Protected optimizer deployment

Build `backend/Dockerfile` from the same source and dependency lock as the API/worker deployment. The image contains the offline dependencies; wizard execution does not install missing built-in packages. Secrets belong in the trusted parent environment, never the image. `.dockerignore` excludes `.env*`.

## Vercel images

Push a **linux/amd64** image to the selected project's Vercel Container Registry (VCR), wait for its repository state to become **Ready**, and resolve the immutable digest. Set `VERCEL_SANDBOX_IMAGE` to that verified image. It must contain `@sha256:` followed by the complete 64-character digest. Configure `VERCEL_TOKEN`, `VERCEL_TEAM_ID`, and `VERCEL_PROJECT_ID` only on the parent. A GHCR reference or a mutable `:latest` tag is not a protected runtime profile.

When extending a VCR image with zstd layers, publish through the Vercel CLI’s OCI Buildx exporter. Preserve the original compression media types when reusing layers; legacy Docker pushes can relabel zstd blobs as gzip. Verify a real sandbox command after publication even when the image is Ready.

Build the sandbox image with `--build-arg INCLUDE_SHINKA_EVOLVE=1 --build-arg INCLUDE_SANDBOX_SUDO=1 --build-arg INCLUDE_GO_RUST=1`. Build the worker image with `--build-arg INCLUDE_SHINKA_EVOLVE=1` too, because the ShinkaEvolve engine runs in the worker. Vercel runs commands as the image's `USER` (`appuser`, UID 1001) and runs a `sudo: true` command through the box's own `sudo` binary. The sandbox image ships `sudo` with a NOPASSWD rule for `appuser`, as Vercel's managed images do, because the `[run]` supervisor needs root. Only the parent's own `sudo: true` commands reach root. The Vercel provider starts every non-root command through `/usr/bin/setpriv --no-new-privs --inh-caps=-all --ambient-caps=-all`, so the box image must have `/usr/bin/setpriv`. Vercel starts every command with all Linux capabilities in its ambient set, so without the drop the non-root box user could write root-owned files such as `/etc`, `/usr/bin` and the standard library (SKY-901). Every image built from `backend/Dockerfile` has `/usr/bin/setpriv` (util-linux). On an image without it, each command fails; no command runs without the block. Every process that command starts keeps the Linux `no_new_privs` flag, and the kernel then ignores the setuid bit of `sudo`. So Codex, which runs as `appuser` with its own sandbox off, cannot rewrite `/etc/codex/requirements.toml` (SKY-389), and the `[run]` entry cannot get root (SKY-398). The sandbox image build fails when `/usr/bin/setpriv` is missing. API/worker images ship no `sudo`. The image build writes the requirements file root-owned and mode 0644, and the parent only reads it back before Codex starts. Only a box that lacks the file, such as the local Docker box with its empty `/etc/codex` mount, gets the root write; on a Vercel image without the file, the root write runs through the image's `sudo`, and an image without `sudo` fails Codex setup closed.

Code from before the sudo image starts user code as plain `bash`, without `no_new_privs`. On the sudo image, the box's NOPASSWD `sudo` then gives that user code root. To roll out, deploy this code to every worker first, and only then pin the sudo image in `VERCEL_SANDBOX_IMAGE`. To roll the code back to a commit before the sudo image, do these steps in this order:

1. Pin a no-sudo image in `VERCEL_SANDBOX_IMAGE` again.
2. Cancel or wait out the runs that use the sudo image. A run keeps the first image it opens, and a resume reuses it.
3. Then deploy the older code.

Vercel does not execute Docker `CMD` or `ENTRYPOINT`; Skynet starts each command explicitly. `WORKDIR` is honored. The engine does not run in the image: the worker runs it. Boxes run the repository setup (one setup box for each run makes the after-setup state, `core/sandbox/snapshots.py`), scorer dependency resolution, step commands, scorers, metrics and stages. A box can also run the guest runner, such as the outer box of a paid Continue check, a debug preview or a completed-run interaction. A guest runner box runs the image's own `/app` copy of the backend with the image's Python and dependencies, and the parent ships only the request. The two share one contract, `SANDBOX_PROTOCOL` in `core/worker/sandbox_protocol.py`, covering the request and event shapes; bump it whenever either changes, including an added request field, which an older image's models drop without an error (`core/worker/tests/test_sandbox_protocol.py` pins the request shapes per protocol). Before sending a request, the worker reads the image's own protocol from that module and refuses an image that lacks it (built before it existed) or speaks another one, asking for a rebuild. Worker dependency or Python updates never block a sandbox. A run records the image it first opens on the job (`sandbox_image`), and every later box for that run, including a box after a resume or a redeploy, boots from that image. Rebuild and re-pin the image to ship image changes to new runs. Image publication and dependency installation alone do not establish that a live setup check succeeded. [Vercel image documentation](https://vercel.com/docs/sandbox/concepts/images)

Keep runtime networking disabled. The parent owns model dispatch, sandbox controls, credentials, cumulative budget reservations, and final usage settlement. Guests use separate scoped capabilities through the stdout/file mailbox. Anthropic Messages, Chat Completions, and the bounded stateless Responses path share this metered dispatch boundary.

Every run uses the engine loop (`core/worker/engine_loop.py`, hosted by `core/worker/loop_host.py`) and keeps no box alive for the whole job. The worker runs the engine loop and its model calls with no box open. Each engine command opens one box for one step, commits that step to the step log, and the box then stops. Each call of the run's repository scorer is one `evaluate` step (`blackbox/repo_scorer.py`). That step opens its own candidate box, its own metric box, and one box for each `[target.<name>]` stage (see Repository scoring boxes). The metric box gets the metric files, the case, its model route, the candidate box's output, and the parent's answers to the metric's stage calls, `[services.<name>]` requests and MCP server calls. The metric box never gets the candidate tree, so no candidate code reaches the metric. A resume replays the step log: each committed step gives its recorded result, with no model call and no box, and real work starts again at the first new step. Each paid Continue check runs in one outer box (`blackbox/preflight.py`). The outer box asks the API process (the trusted parent) to score, and the parent opens the scorer boxes (`core/api/preflight_execution.py`). A fresh wizard path has two Continue checks (Evaluation and Optimization) plus the submitted run; matching evidence retries reuse the completed check rather than opening another session. Python scorers also use one dependency-resolution session when a matching lock is unavailable, before the full readiness check. The runtime estimate includes this additional setup session.

## Local Docker sandbox (local mode)

With `APP_LOCAL_MODE=1` (the Mac app), the protected parent opens its boxes as containers on the local Docker daemon instead of Vercel microVMs. The async Docker provider in `core/sandbox/providers/docker.py` implements the same `SandboxEnvironment` contract as the Vercel provider, and the sync bridge in `blackbox/sandbox_runtime.py` opens both, so the model mailbox, the sandbox broker and the guest protocol do not change. Hosted deployments (local mode off) still accept only Vercel.

- **Image.** `APP_LOCAL_SANDBOX_IMAGE` holds a local image id (`sha256:<64 hex>`), built from `backend/Dockerfile` and read with `docker image inspect --format '{{.Id}}'`. In local mode only this bare id is accepted as the deployment image; a user image pinned by registry digest is also accepted (see User images). The current Dockerfile installs x64-only harness packages, so on Apple silicon build it with `--platform linux/amd64`.
- **CLI.** `APP_DOCKER_BIN` selects the Docker CLI (default `docker`). OrbStack works through the same CLI.
- **Isolation.** Each box runs `docker run -d --rm --init --network none --read-only --cap-drop ALL --security-opt no-new-privileges --pids-limit 1024 --cpus <vcpus> --memory <vcpus × 2048>m`, with no published ports. Only the tmpfs mounts `/workspace` (the working directory and `HOME`) and `/tmp` are writable. The box's only process is `sleep <lifetime>`, so the container and every command in it end at the wall-time limit. Commands run through `docker exec` in their own process group, and a timeout kills that whole group.
- **Streaming.** Command output is read line by line while the command runs, so the model mailbox answers guest model requests mid-command. File writes use a separate `docker exec` with a tar stream and can run beside an in-flight command.
- **Setup boxes and registries.** A box that needs package registries during setup (`allowed_hosts`, set to `PACKAGE_REGISTRY_HOSTS`) never joins Docker's `bridge`: on Docker Desktop that network reaches services that listen only on the Mac's loopback, through `host.docker.internal` (192.168.65.254), and the internet at large. Instead the box gets its own `docker network create --internal` network with no route to the internet or to the Mac's loopback. That network's gateway address is the Docker VM itself, so services that listen on the VM (for example rpcbind on port 111) stay reachable from the box. Its only way to the internet is an egress proxy sidecar (`docker_egress_proxy.py`, standard library only) that runs on the box's own image, joins that network and `bridge`, and runs with a read-only root, no capabilities and user 65534. The box reaches it through `HTTPS_PROXY`/`HTTP_PROXY` (both cases, plus `npm_config_https_proxy`/`npm_config_proxy`), which pip, uv, npm, yarn, cargo, go and git read. The proxy tunnels only `CONNECT <exact allowlisted host>:443`, and only when every address the host resolves to is public; it then connects to that checked address. It refuses any other host or port, any plain HTTP request, raw IPs, and names that resolve to the Docker host range, private, loopback or link-local addresses. A tool that ignores the proxy variables finds no route and fails. When the workspace switches the box offline, it disconnects the box, probes that the hosts are unreachable, and removes the proxy and the network.
- **Labels.** Every box, egress proxy and setup network has `skynet=blackbox` and `skynet.job=<owner>`. When a job ends abnormally, the worker removes the job's leftover containers by the `skynet.job` label and then its networks. A killed backend runs no such cleanup: `--rm` and the `sleep` lifetime remove the box and its proxy, but the setup network stays, and each one holds a /16 of Docker's address pool. So in local mode the worker removes every `skynet=blackbox` network with no attached container when it starts. It skips networks younger than 5 minutes, because a box that is still opening has a network with no container yet, maybe in another worker or backend on the same Docker daemon. It logs a failure and goes on. The desktop shell's quit sweep removes containers by the `skynet.job` label only, not networks.
- **Cost.** Local boxes are never billed: no Vercel quote, no budget reservation, and `runtime_cost_profile(..., "docker")` reports zero bounds.
- **Preflight.** `docker_sandbox_unavailable_reason` reports `sandbox.docker_unavailable` when the CLI is missing or the daemon does not answer, and `sandbox.docker_image_missing` when the image id is unset or not present.

Known gaps against Vercel: the setup box's egress has no byte cap (Vercel's `SANDBOX_NETWORK_BYTES_CAP`), and the proxy allows port 443 only. The box and command environment reach each command over stdin, never as `docker` arguments, because the box environment can hold the gateway key. tmpfs pages count toward the container's memory limit.

## User images (SKY-889)

A box can start from a user image instead of the deployment image. A user image is a `name@sha256:<64 hex>` reference in a neutral OCI registry, plus optional (username, password) pull credentials. A box with no user image starts exactly as before. A user image must match one strict reference grammar, `[host/]path@sha256:<64 hex>` (`digest_image` in `providers/docker.py`). It refuses a leading `-`, so the reference can never be a CLI option, and any `@` or user info before the digest. The image builder and its registry are SKY-888 (build and store user images); this part takes only the reference and the credentials.

- **Protected execution.** `bind_protected_sandbox` accepts an `image` that is the deployment's own immutable reference, as before. A user image comes as `source_image` instead, and it needs `user_image_repository` (the owner's repository in the SKY-888 registry). The bind fails closed: a `source_image` with no owner repository, or next to an `image`, raises `UnpricedOperationError`. The user image must lie under that repository, pinned by digest (`trusted_user_image(image, repository)`). This holds in local mode too, although its deployment image is a bare `sha256:` id. A mutable tag, a short digest, another owner's repository, another host (for example `10.0.0.5:5000/x@sha256:...`) or a reference outside the strict grammar raises `UnpricedOperationError`. With no `image`, the deployment image is used, as before.
- **Vercel.** Vercel Sandbox starts only from its own registry (VCR). `VercelEnvironment(source_image=..., pull_credentials=..., copy_image=...)` first calls the injected copier, which copies the image into VCR and returns the copy's digest reference. The box is then priced and created from that copy. The copy runs before the box's own reservation, with a limit of `COPY_TIMEOUT` (1 hour). The provider also needs `user_image_repository` and refuses an image outside it. Each process copies one source digest into one Vercel team and project once for each owner repository. The cache key is the source image, the owner repository, and the Vercel team and project. It holds no credentials, because the run's pull token renews about every 45 minutes. Boxes of the same owner share one copy, also when their credentials are different. Another owner copies again. Later boxes with the same key reuse the copy, and boxes that start at the same time wait for one copy. Each waiter is shielded: a cancel of one box does not stop the copy for the others. The copy is cancelled only when its last waiter leaves. A failed or cancelled copy is not kept. A failed copy, a time-out or a result that is not pinned by digest raises `ImageCopyError`, a `SandboxInfraError`, and no box is reserved or created. Its message names only the error type, because a copier message can echo the credentials. A box from a snapshot skips the copy. A user image with no copier raises `SandboxFatalError`. The copier is `VcrCopier` (`core/sandbox/vcr_copy.py`, SKY-898). The worker has no Docker daemon, so it copies with plain OCI Distribution calls. It reads the manifest and blobs from the source registry with the pull credentials and pushes them to `vcr.vercel.com/<team>/<project>/user-<owner>` by digest. VCR takes HTTP Basic auth as `oidc` with a project OIDC token from `POST /projects/<id>/token`, the same token that `vercel vcr login` gets. Blobs that VCR already holds are skipped. An index copies only its linux/amd64 image, so the copy has that image's digest. The copier waits until VCR no longer lists the image as `preparing`. The bridge gives the copier to every hosted Vercel runtime that has `VERCEL_TOKEN`, `VERCEL_TEAM_ID` and `VERCEL_PROJECT_ID`. On a billable provider, the bridge wraps the copier in `metered_copier` (`core/sandbox/bridge.py`). Before each new copy, it reserves the copy's time limit (`image_copy_usd(COPY_RESERVE_SECONDS)`) on the run budget. After the copy, it settles the started minutes, also for a failed copy. A reused copy calls no copier and costs nothing. When the run cannot fund the copy, `BudgetError` stops it before it starts, and the provider passes that `BudgetError` on unchanged, not as `ImageCopyError`.
- **Docker.** A digest image that `docker image inspect` does not find is pulled with `docker pull` before the box starts, with a 30-minute limit. A cancel kills the pull at once, because a pull creates no container. `docker run` still uses `--pull never`. With credentials, the pull uses its own temporary `--config` folder that holds the auth, never the command line, and `-H` with the current context's daemon address. A tag or a local `sha256:` id is never pulled. A failed pull raises `SandboxInfraError`. Docker Hub references (no host, `docker.io`, `index.docker.io`, `registry-1.docker.io`) use Docker's own `https://index.docker.io/v1/` auth key; Apple logs in to `docker.io` for them (`registry_host`). Gap: `-H` keeps the daemon address but not a context's TLS material.
- **Apple container.** The provider already pulls its image. With credentials it first runs `container registry login --password-stdin <host>`, so the password goes only over stdin. A cancel kills the login and the pull at once. The login stores the credentials in the macOS Keychain, as a manual login does. A failed login stops the start. Gap: it is not verified that the CLI boots a local image by its `sha256:` id without a pull.
- **Daytona.** The digest image goes to Daytona as it is, and Daytona pulls it. Daytona takes no pull credentials per call: a private registry needs an entry in the Daytona organization (for ECR, an IAM role that Daytona assumes). So the provider takes no credentials.

## Repository scoring boxes

A repository run scores each version in two new boxes (SKY-398), plus one
new offline box for each `[target.<name>]` stage. The candidate box opens
from the saved after-setup state and runs the `[run]`
entry. The metric box opens from the saved metric state and holds only the
metric files and the runner. Each box has its own `operation_key`, so each
reserves its own hold. On Vercel the saved states are snapshots. In local
Docker mode they are tar files that the parent keeps, because a box keeps
`--read-only` and the parent does not use `docker commit`. `SandboxSpec`
names the state in `snapshot_id` or `snapshot_archive`. The opener checks the
prepared tree's digest before it lays out a version. The stage boxes open
before the metric runs. The metric reaches a stage with `call(name, input)`,
the parent runs the stage in its box, and it writes the answer back into the
metric box.

The metric setup box makes the saved metric state once for each run
(`RepoWorkspace._setup_metric`). It opens with `private=True`, no services,
no secret and the package registry hosts (`PACKAGE_REGISTRY_HOSTS`) as its
only network. It installs the packages of `.optimize/metric-requirements.txt`.
When `ascent.toml` sets `[metric] setup` (SKY-740), it then installs the
metric files into `.app-metric/repo` and runs the command there once, with
the 30-minute setup time limit. A failed or timed-out build raises
`RepoSetupError` with the redacted last lines of its output, before any
candidate box opens. After the build, the box removes the metric files
again, so the saved state holds the build output but no metric source. The
parent then saves the box state. The saved state can be the box working
folder only, so files that the build writes outside it may not be kept;
build into the metric files' folder. Files inside the working folder are
kept and enter every metric box. Local Docker boxes and the local runtime
set `HOME` to the working folder. The image sends the Go and Rust caches to
`/tmp` (see the table below), but the local runtime does not, so there
`~/.cargo` and `~/go` stay in the saved state. A metric setup should keep
its caches small, for example with `CARGO_HOME` or `GOMODCACHE` under
`/tmp`. Each metric box then extracts the metric files over that folder again, so the built files stay next to them.
The box has its own `metric-setup` operation key, so its time counts in the
run's cost.

The parent starts the `[run]` supervisor with `sudo: true`, through the model
mailbox, so the entry keeps its model route. On Vercel the root exec wrapper
first makes a root-owned `/tmp/.app-root-output-<token>` folder with mode 0755.
It stops if anything is already at that name. It sends the supervisor's
stdout to `output.out` in that folder. The supervisor checks that file and
its folder, then starts the entry as the owner of the
candidate tree, so the entry cannot write the wrapper's files. Before the
switch, the supervisor sets `no_new_privs` on itself, so the entry cannot use
the box's `sudo` to get back to root. If it cannot set the flag, it does not
start the entry. A root command gets only the system folders on `PATH`, from
the image's `sudo` rule and from the provider, because the box user can write
`/app/.venv/bin`. Those folders are root-owned, and the box user cannot write
any program file in them. Vercel's in-box agent starts `sudo` itself, so the
image puts a root-only guard folder, `/usr/local/libexec/skynet-path-guard`,
with one link to `/usr/bin/sudo`, first on its `PATH` and its login shell
`PATH`. A `sudo` that the box user plants in `/app/.venv/bin` is then never
found first. How the agent finds `sudo` is not verified on a real box; check
it on a real box before you pin the sandbox image. After the switch, the
entry gets the image's box `PATH` from `APP_ENTRY_PATH`: the guard folder
first, then `/app/.venv/bin`. In a local
Docker box the supervisor's stdout is a pipe and its root has no
capabilities, so it cannot switch users and the entry runs as the
supervisor's user. A root with capabilities switches users also with a pipe.
Only the supervisor command gets a root model proxy. That proxy starts from
`/usr/local/bin/python3` and runs only the proxy and config bytes whose
digests the parent sent. `test_metric_isolation.py` proves the user switch on Docker with a
privileged `docker exec` that stands in for Vercel's root.

`sandbox-runtime/package-lock.json` locks the CLI dependency graph and package integrity. So the worker image needs the switch. A worker without the interpreter fails a single ShinkaEvolve run with `blackbox.shinka_interpreter_missing`. In Auto, the ShinkaEvolve lane fails and the other lanes go on. The engine readiness check of a Continue check runs in the API process, which uses the same backend image as the worker (`infra/terraform/scripts/build-push.sh` builds one image for both, with `--build-arg INCLUDE_SHINKA_EVOLVE=1`). It reports `shinka_ready` when `/opt/shinka/venv/bin/python` is executable, is Python 3.12 or later and finds the `shinka` package, and `autosaddler_ready` the same way for `/opt/autosaddler/venv/bin/python` and `autosaddler`. When one is false, a Continue check refuses a single run of that engine. The check reads the API's image, so it is true for the worker only while both services run the same image. The eve launch builds a temporary project outside the workspace. When the image has eve, the project links each preinstalled package into its own `node_modules`, so `eve build` runs with no registry. Its tools run in the run workspace through a Skynet sandbox provider. Python dependencies come from `uv.lock` or the selected complete requirements lock.

Codex uses Responses and disables transport retries/websockets in its generated provider configuration. OpenCode's pinned package bundles its OpenAI-compatible provider; the protected profile disables model-catalog refresh, updates, default auth plugins, and language-server downloads. Built-in readiness checks verify exact CLI versions in the selected sandbox. Authored dependency commands run in the same offline sandbox boundary and may use only packages already installed in the pinned image. Scorer and agent dependencies are installed during their paid Continue check; command syntax that requires a real candidate remains separately verified without inventing one. Missing offline dependencies fail setup clearly. The submitted run repeats preparation in its own boxes, so readiness evidence never substitutes for run isolation.

## Scorer packages

Python scorer setup inspects imports in the selected sandbox and resolves missing distributions against the account registry (Settings → Optimization; PyPI by default). Optional package requirements disambiguate import names and version constraints. Resolution uses pip 26.2.1 and accepts wheels with SHA-256 hashes only; source distributions and direct URL requirements are unsupported. The parent brokers bounded registry downloads through a separate package-only mailbox capability, with DNS pinning, TLS verification, and no redirects. Sandbox networking remains disabled.

The signed lock binds exact wheel versions, URLs, and hashes to the scorer source, Python patch version, and immutable sandbox image. Subsequent checks and runs install these artifacts into the private scorer workspace using `--no-index --no-deps --require-hashes`. An altered lock or changed source/image requires resolution again. The full scorer check executes after installation; resolving packages alone is not successful scorer evidence. Resolution and scorer checks use the same authorized setup budget and preserve pending usage and budget stops. Built-in image dependencies remain bound to the image digest. Registry downloads are limited to 256 MiB per wheel and 512 MiB per dependency set.

Candidates the optimizer writes later may import packages the lock never saw. Before such a candidate scores, the parent scans its imports and runs the setup script's `extend` action in the same box: missing roots resolve against the account registry with every locked distribution pinned as a constraint, and only the new wheels install. The relay therefore keeps the index reachable under a lock, bounded by the same budget check and download ceiling. A candidate whose packages cannot be installed receives that failure as scorer feedback.

The image ships OSMesa (`libosmesa6`, `libgl1`, `libglu1-mesa`) and the scorer runs with `PYOPENGL_PLATFORM=osmesa`, so PyOpenGL-based renderers such as pyrender work without a display or GPU.

## External evaluators and tools

User-selected remote evaluators keep their original `POST {candidate, case}` protocol. The parent retains the selected endpoint and bearer credential, pins its permitted DNS address, verifies TLS for the original host, and disables redirects and transport retries. Private/loopback endpoints require the existing explicit `DISCOVER_ALLOW_PRIVATE` deployment opt-in; cloud metadata addresses remain denied. The guest receives an opaque evaluator-only capability, separate from model, tool, and sandbox controls.

External evaluator and MCP service fees are outside Skynet Total. Their relay still checks the owning execution generation and cancellation state; it does not invent zero-cost provider receipts. Every hosted Anything setup and run requires the deployment's managed Vercel profile. The external endpoint call leaves through the trusted parent relay, while target and scorer execution stay in boxes. The engine runs in the worker. A supplied seed is scored on a non-held-out case, and an HTTP failure remains a failed check with the original status. Seedless setup verifies endpoint readiness and clearly defers the actual request until a real candidate exists.

## Skynet-keyed connectors

`core/billing/env_connectors.py` lists the hosted MCP connectors that Skynet pays for: `maps` (Google Maps Grounding Lite), `web_search` (Firecrawl) and `browser` (Browserbase). Each catalog entry gives the hosted MCP URL, the config setting that holds Skynet's key, the allowed tool names and the USD price of one call.

- A run asks for connectors with `env_connectors: ["maps", ...]`. The parent gateway opens one `McpToolsBroker` for each connector, with its own scoped token, beside any user `live_mcp` roster. The guest gets only `_skynet_connector_routes` (gateway URL and token). It never gets the provider URL or the key.
- A connector with no key in config (`GOOGLE_MAPS_API_KEY`, `FIRECRAWL_API_KEY`, `BROWSERBASE_API_KEY`) is not offered. Setup fails with a message that names each missing connector and its setting.
- Each `tools/call` reserves the tool's catalog price through `operation_quote` before the provider sees it, and settles that price as a `tool` cost with the connector name as its role. A call that does not fit the budget is refused before dispatch. A call that fails before the broker sends the tool request (an admission stop, a connection or `initialize` failure) releases its hold. A call that fails or is interrupted after the send settles at the catalog price, because connectors have no usage reconciler. Tool listing is free. A tool name outside the catalog is refused.
- The broker redacts each key header and query value from tool results. Keys never enter the payload, the run record or an error message.
- Applying connector lists to boxes and the guest environment wiring belong to SKY-354.

## Recovery contract

A worker that goes away does not end the run. The orphan sweep (`recover_orphaned_jobs` in `core/storage/remote.py`) requeues each funded active run whose lease expired. The run keeps the same job and cumulative funded budget. The requeue fences the previous execution generation, and the new generation waits for unresolved prior usage before it admits new work. The new generation opens the same step log and replays each committed step, with no model call and no box, until it reaches the first new step. A run with no committed step and no checkpoint starts again from the beginning. A run with committed steps gets at most `MAX_AUTOMATIC_RESUMES` (4) automatic resumes; other automatic requeues count against `job_max_attempts`. A graceful worker restart counts against neither. `recover_orphaned_jobs` and `requeue_for_resume` are the source of truth for the cases below. When the remaining budget cannot cover the resume, the run stops with `stop_reason=budget_reached`. When a user cancel or pause races the sweep, the run keeps the user's status. The sweep fails every other run that it cannot requeue, with `stop_reason=interrupted`. These are a run at `MAX_AUTOMATIC_RESUMES` or `job_max_attempts`, and a run whose prior usage makes no settlement progress for `ORPHANED_USAGE_WAIT`. The usage-wait stop keeps the interrupted budget generation (`recovery.interrupted_budget_generation`, from `_interrupted_recovery`). A user stop that races the sweep also keeps it, when the run has one. A cap stop does not keep it.

The owner can also Resume a run manually. The resume checks in `core/api/routers/optimizations/lifecycle.py` and `_resume_candidate_id` in `core/api/routers/_helpers.py` are the source of truth. Resume is offered for a `failed`, `cancelled`, `paused` or budget-stopped run that has a saved GEPA checkpoint or keeps the interrupted budget generation (`is_interrupted_stop`). Only GEPA writes checkpoints, so for every other engine manual Resume needs that kept generation. A run that the sweep failed at an automatic resume cap does not keep it, so without a GEPA checkpoint it offers Retry or Clone. A run stopped at `MAX_AUTOMATIC_RESUMES` has an attempts count of 4 or more, at or above the default `job_max_attempts` (3). So even with a GEPA checkpoint, Resume is offered only when `JOB_MAX_ATTEMPTS` is above its attempts count. The resume replays the step log in the same way. A saved checkpoint must still pass its compatibility checks, which include the run's pinned sandbox image. Any other stopped run offers Retry or Clone. Manual resumes count against `job_max_attempts`, except a resume of a paused run, of a budget stop or of a worker-restart stop.

Budget-reached stops and user cancellation are never resumed without the owner. A fresh restart returns to configuration for fresh authorization. A stopped run retains only an upstream-selected evaluated incumbent, with explicit final-evaluation evidence; no-result stops remain distinct from failures and from evaluated results.
