# Skynet Design Context

This document records the product and design system currently implemented in the repository. It is descriptive, not aspirational. When this document conflicts with the application, the current code is the source of truth and this document should be updated to match it.

## Design Context

### Users

Skynet is built primarily for non-technical data analysts who need to turn datasets into tagged data, optimized LLM programs, and usable inference workflows without writing application code.

The implemented interface also supports technical operators and administrators through code editing, model configuration, storage management, API access, billing, observability, and deployment-oriented details. These capabilities are progressively disclosed so they do not dominate the default analyst experience.

### Core Jobs

Users can currently:

- Upload CSV, JSON, XLS, and XLSX datasets and manage them in a personal or shared dataset library.
- Edit datasets in a spreadsheet-style interface and inspect dataset usage.
- Tag rows manually or use copilot/autopilot assistance with an interview, rubric, calibration, review, provenance, confidence, and bulk auto-tagging.
- Share labeling sessions Drive-style (invited members and anyone-with-link at viewer/editor tiers, ownership transfer); shared-in sessions list in the chooser, editors co-annotate, viewers browse the results table and page through rows read-only.
- Configure and submit repository optimization runs through a guided multi-step wizard.
- Select generation, reflection, and judge models and adjust optimization parameters.
- Author or generate scorers, cases, and repository code.
- Monitor live and historical optimization jobs from the dashboard and sidebar.
- Inspect analytics and explore searchable results.
- Review optimization details, progress, logs, trajectories, prompts, examples, and scores.
- Test optimized programs through inference surfaces and export or share results.
- Organize runs into folders and share runs, folders, datasets, labeling sessions, and agent chats through share links.
- Serve a finished run, inspect its reward, schedule reruns, and read usage and cost per run.
- Resume a saved run setup (a setup draft) and edit metric code in the wizard's IDE workspace.
- Manage storage, API tokens, provider keys, connectors, notifications, billing and wallet credits, preferences, language, color theme, and agent trust.
- Get guided help from the first-login intake interview, the setup tour, the public docs site, and the agent panel (with a reasoning-effort control).
- Link the Mac desktop app and approve MCP agent access.

### Brand Personality

The implemented product feels:

- **Capable:** advanced optimization, tagging, analytics, and agent workflows are presented as serious working tools.
- **Guided:** steppers, interviews, recommendations, help tips, empty states, and tutorials keep non-technical users oriented.
- **Restrained:** the warm neutral palette, a single terracotta accent, compact typography, and flat surfaces avoid a loud “AI product” aesthetic.
- **Technical when necessary:** code, model identifiers, metrics, IDs, and structured data use explicit technical treatments rather than being hidden.

### Aesthetic Direction

Skynet uses a warm, flat application theme in light and dark variants. Surfaces are warm off-white and cream (light) or bronze-brown (dark). One terracotta (rufous) accent carries primary actions, focus, links, and the main chart series. Teal, amber, blue, and red are reserved for status. The animated SKYNET wordmark provides the technical edge; the working surfaces remain approachable and calm.

Users choose System (the default), Light, or Dark in Settings → Account. The first-login intake and the agent can also set it. The choice is stored in a cookie with a localStorage copy. A pre-paint script resolves it and puts a `.dark` class and the matching `color-scheme` on `<html>`, and every color token switches off that class (`frontend/src/shared/lib/color-theme.ts`). The public docs site has its own theme toggle. The toast container still passes `theme="light"`.

The interface favors functional density over marketing-style whitespace. Narrow setup and summary flows are centered, while tables, editors, tagging, trajectories, and agent-assisted work expand to use the available viewport.

## Current Product Structure

### Primary Navigation

The implemented sidebar exposes:

- Dashboard
- Data — a hub whose segmented tabs cover the dataset library (`/datasets`) and the labeling-session chooser (`/tagger`); dataset cards offer a "Tag this dataset" quick action that deep-links into tagging setup
- New optimization
- Explore

The sidebar also contains optimization history, owned/shared views, active-job state, storage usage, account controls, and contextual job actions. The run list has Mine/Shared tabs, folders, a filter menu, and a new-folder button.

The sidebar is resizable from 210–420 px (default 240 px). Dragging it below 150 px collapses it to a 64 px icon rail; dragging past 196 px expands it again. The drag handle is the only collapse control, and the state persists under `app.sidebar.collapsed`. The desktop header also holds a balance chip and a notification bell. Below 768 px the app switches to the phone shell described below; the desktop shell's off-canvas drawer and menu button (`md:hidden`) never show after hydration.

### Phone Shell (viewports below 768 px)

Skynet on a phone is a **view-first companion**, not a smaller desktop. Authoring is desk work and stays on laptops/desktops; the phone is for checking on runs and results.

- Chrome: a fixed 53 px header (wordmark, global search, notification bell) and a fixed 56 px bottom tab bar (plus safe-area inset) with three tabs — Home (`/`), Explore (`/explore`), Account (opens the account menu: Settings, Docs, Downloads, Terms, Privacy, Source code, Log out). The agent pill docks just above the tab bar; the agent panel opens as a full-screen sheet.
- Home shows the dashboard stats plus a tappable job-card list (name/ID, status, type · module, age, elapsed, score). No selection, column filters, resize, or export.
- Run detail keeps Overview, Serve (`playground`), Artifact (`best`, repository runs with a result only), Reward, Logs, and Usage and cost (`PHONE_DETAIL_TABS` in `frontend/src/features/optimizations/lib/detail-tabs.ts`), and two header actions, Share and Cancel. Data, Code, Scheduled run, Config, Clone, Resume, Configure new, Pause, Delete, and the Storage link are desktop-only; deep links to a hidden tab land on Overview. Old `lm-activity` and `budget` links open Usage.
- Explore keeps search, results and sorting; filters open in a bottom sheet.
- Settings shows every tab on a phone. It opens on Account.
- Every route renders on a phone. Device class selects navigation chrome only, never route or settings access.
- The device class is `matchMedia("(max-width: 767px)")` on the client (`useIsPhone()`), seeded on the server from `Sec-CH-UA-Mobile`/UA so the first paint already picks the right shell.

The fixed header includes a global search trigger. It opens a command-style palette for quick actions, primary destinations, and settings sections, with Cmd/Ctrl+K as a keyboard shortcut.

### Implemented Routes

- `/` — job dashboard; analytics at `?tab=analytics`
- `/submit` — optimization submission wizard
- `/optimizations/[id]` — optimization detail and result workflow
- `/tagger` — labeling-session chooser and new-session setup
- `/tagger/[id]` — resumed interview, annotation, calibration, review, and auto-tagging session
- `/datasets` and `/datasets/[id]/edit` — dataset library and editor
- `/datasets/share/[token]`, `/folders/share/[token]`, `/tagger/share/[token]` — share-link redeemers that attach the item to the account
- `/share/[token]` — shared run
- `/share/chat/[token]` — shared agent chat
- `/explore` — searchable public/result corpus
- `/storage` — storage usage and cleanup
- `/download` — desktop app downloads
- `/desktop/link` — consent to link the Mac app
- `/mcp/authorize` — consent for MCP agent access
- `/docs/[[...slug]]` — public docs with their own header
- `/terms` and `/privacy` — legal pages (forced LTR)
- `/login` — authentication

Settings is a dialog, not a route. It opens from the account menu and Cmd/Ctrl+K. Its tabs are Optimization, Tagging, Agent panel, Account, Notifications, Security, Privacy & data, Billing, Usage, Providers, Connectors, API, Admin (admins only), and About; the Mac app drops the hosted-only tabs.

These render without the standard application chrome: `/login`, `/share/[token]`, `/download`, `/desktop/link`, `/mcp/authorize`, `/terms`, `/privacy`, `/docs`, `/share/chat/[token]` for signed-out readers, and `/optimizations/[id]` for signed-out viewers of public runs. The desktop shell does not wrap `/tagger` routes in its page container; they pick their own width. The phone shell wraps every other route, `/tagger` included, in its page container.

### Workflow Model

The dominant interaction model is progressive disclosure:

- Setup wizards reveal one decision at a time and validate before advancing.
- Text tagging begins from the Data hub: resume an existing labeling session, start a new one, or jump in from a dataset card with that dataset preselected.
- Advanced sections remain reachable but are collapsed by default.
- Assist mode changes which questions and steps are relevant.
- Agent interviews ask one focused question at a time and end in an editable artifact.
- A run setup in progress saves as a server draft that the user can resume.
- Long-running work streams progress and supports retry, resume, cancel, or fallback polling.
- User state is preserved through URL parameters, local preferences, drafts, autosave, and persisted sessions.

The dark theme is bronze-brown, and the stylesheet states that every text pair clears WCAG AA. Its accent splits in two: the deep `#B4521F` stays as the fill, and the lighter `#E0935A` serves as text and ring.

Run status has its own tokens: success is teal, failed is red, running is blue (so it never reads as failure), and pending, paused, and cancelled sit apart by lightness (`--status-*`). Agent trust levels use `--trust-ask` (blue), `--trust-auto-safe` (green), and `--trust-yolo` (red). The candidate tree uses `--tree-*`, with a gold winner. Code uses `--code-*` syntax tokens per theme.

Charts use `--chart-1`…`--chart-5`: three terracotta-to-sand steps, then two blues (light) or one blue and a warm grey (dark). Progress uses `--gradient-progress` (light `#8F4318` → `#B4521F` → `#CF7A3A`; dark `#B4521F` → `#E0935A` → `#F0B98A`). The accent stays scarce; most hierarchy comes from typography, spacing, surface tone, and borders.

### Typography

- Onest Variable is the default Latin/Cyrillic UI face (`--font-ui`).
- Heebo Variable is used for Hebrew.
- Arabic, Persian, Devanagari, Japanese, Korean, and Chinese (`zh-Hans`, `yue`) prepend script-specific variable Noto/Vazirmatn families, with Onest kept after them. The font switches from `<html lang>` with no JS.
- JetBrains Mono Variable (ligatures off) is reserved for code, IDs, model names, shortcuts, and structured technical values.
- `h1` and `h2` use Bricolage Grotesque Variable (`--font-display`) at weight 700 with optical sizing. Bricolage draws only Latin, so other scripts fall through to the locale's UI font. `h3` uses the UI face at weight 700.
- Product UI primarily uses compact fixed sizes from approximately 11–16 px, with stronger contrast in weight rather than many near-identical sizes.

### Surfaces

The UI is flat. In-page surfaces carry no shadow by design: `--shadow-sm`, `--shadow-card`, `--shadow-hover`, and `--shadow-inset` are all `none`. A 1 px border and a background tone separate surfaces. Only true overlays — dialogs, popovers, menus, tooltips, toasts, sheets, and the tour card — use `--shadow-float`. Known exceptions: the submit wizard's RunOverview panel uses `shadow-lg`, the agent panels (`GeneralistPanel`, the docs agent panel) cast a custom side shadow instead of `--shadow-float`, and the effort slider track uses small inset shadows.

The shared card primitive (`frontend/src/shared/ui/primitives/card.tsx`) uses:

- `rounded-2xl`
- A solid `bg-card` fill
- A low-contrast `border-border/50` border that firms up on hover to `#C8B9A8` (light) or `--input` (dark), with no shadow
- Light backdrop blur
- `--spotlight-x` / `--spotlight-y` set on pointer move; no style reads them yet, so no spotlight renders

Popovers use `rounded-xl`, a translucent background with strong blur, and `--shadow-float`. Dialogs use `rounded-lg`. The base radius is `--radius: 0.5rem`.

Dialogs, popovers, tooltips, sheets, tables, tabs, buttons, badges, inputs, and switches build on the shadcn/Radix primitives in `frontend/src/shared/ui/primitives/`. Components should reuse these primitives and existing tokens before introducing one-off styling.

### Controls

- Primary buttons use the terracotta `--primary-fill` with white text and darken to `--primary-hover`.
- Variants: default, secondary, outline, ghost, link, destructive. Sizes: xs, sm, default, lg, pill-sm, pill, pill-lg, and icon sizes. Rectangular buttons use `rounded-md`; pills use `rounded-full`.
- Press feedback scales to 0.97 over 75 ms; reduced motion turns it off. Hover feedback is brief and restrained.
- Focus-visible treatment is component-owned, usually a border plus three-pixel translucent ring.
- Disabled controls preserve shape and hierarchy while lowering opacity.
- Status should use established semantic colors and shared status components.

### Layout and Spacing

- The fixed header is 53 px tall.
- Standard content is capped at `max-w-7xl` with fluid inline padding `clamp(1rem, 5vw - 0.5rem, 2rem)`. Above 1440 px the cap grows to `clamp(80rem, 85vw, 120rem)`, at 1200 px and below it is 90%, and a collapsed sidebar removes it.
- The submit wizard uses `max-w-6xl`; its Metric/IDE step expands to `max-w-screen-2xl`. Inner setup screens use `max-w-3xl` or `max-w-5xl`.
- The tagger intentionally uses the full available work area.
- Desktop chrome reserves space for the fixed inline-start sidebar through `margin-inline-start: var(--app-sidebar-width)`.
- Phone chrome (below 768 px) uses the fixed header + bottom tab bar of the phone shell; content is padded by `--header-height` / `--tabbar-height` (56 px + safe-area inset).
- Existing spacing follows Tailwind’s compact 4 px-derived scale, with common gaps of 8, 12, 16, 24, and 32 px.

## Interaction and Motion

Framer Motion is used for page entrances, step transitions, sliding tab indicators, overlays, agent surfaces, and selected high-value transitions. Typical timings range from 75–500 ms. Shared tokens are `--duration-fast: 120ms`, `--duration-base: 160ms`, and `--ease-snappy: cubic-bezier(0.2, 0.8, 0.2, 1)`; `(0.16, 1, 0.3, 1)` also appears.

Motion communicates hierarchy, navigation, progress, or state change. It should not delay input or obscure data.

Reduced motion is implemented in two places:

- `MotionConfig reducedMotion="user"` applies the OS setting to every Framer Motion animation.
- `prefers-reduced-motion` blocks in CSS disable non-essential animation and transitions.
- New motion must respect both.

## Localization, Direction, and Content

The application currently supports 24 locale entries. English is the product default. Hebrew is the complete base catalog; other locales follow explicit fallback chains. Hebrew, Arabic, and Persian render RTL.

Direction is driven by the active locale at the document and Radix-provider level. Components use logical properties (`start`, `end`, `ms`, `me`, `ps`, `pe`, `inline-start`) and direction-aware icons. User-authored text commonly uses `dir="auto"`; code, model IDs, timestamps, shortcuts, and numeric technical values explicitly use LTR where needed.

UI copy should:

- Use plain language suitable for non-technical analysts.
- Name the user’s decision or outcome, not the implementation mechanism.
- Keep labels short and move explanation into descriptions or help tips.
- Preserve established translation keys and regenerate typed catalogs through the repository’s i18n workflow.
- Avoid embedding untranslated user-facing strings directly in components.

## Accessibility and Resilience

Current implementation patterns to preserve:

- Keyboard-operable buttons, dialogs, menus, tabs, tables, cards, and agent actions.
- Visible component-level focus states.
- Semantic labels and ARIA state on icon-only or expandable controls.
- Reduced-motion handling.
- AA text contrast in both color themes.
- Script-aware font and BiDi handling.
- Content-first source order even when visual navigation is positioned first.
- Skeletons for initial loading, retained content during refreshes, actionable empty states, retry controls, and inline errors.
- Responsive behavior that adapts working surfaces rather than simply hiding core actions.

## Design Principles

1. **The current application is the ground truth.** Match existing tokens, primitives, route behavior, and interaction patterns before proposing a new system.
2. **Guide without patronizing.** Advanced ML workflows should be understandable to non-technical analysts while retaining accurate technical detail.
3. **Reveal controls when they become relevant.** Mode, permissions, data shape, job state, and user intent determine what appears next.
4. **Keep working surfaces efficient.** Dense data, code, tagging, and trajectory views should use available space and minimize unnecessary containers.
5. **Preserve the warm restrained hierarchy.** Use the established warm neutral surfaces, the single terracotta accent, compact typography, flat surfaces, and rare semantic accents, in both light and dark themes.
6. **Treat RTL and localization as structural requirements.** Direction, icon orientation, portals, truncation, and mixed-script content must work in every component.
7. **Make long-running work legible and recoverable.** Stream progress, retain state, explain failures, and provide retry/resume/cancel paths where the underlying workflow supports them.
8. **Respect user control and trust.** Manual, copilot, autopilot, agent trust, color theme, and advanced preferences must meaningfully change behavior rather than acting as cosmetic toggles.
